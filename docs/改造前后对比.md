# 喵喵输入法 · Windows TSF 输入法改造前后对比

> 面向接手的 AI / 开发者。**每个结论都附实测证据和复现方法**，不靠读代码猜。
> 这份文档的重点不是"改了什么"，而是"怎么确定该改什么"——第 3 节的方法论比第 2 节的结论更值钱。

---

## 0. 这个项目是什么

一个**真正的 Windows TSF 键盘输入法**（Text Input Processor），不是键盘钩子、不是自动替换文本的辅助工具。

| 项 | 内容 |
|---|---|
| 项目路径 | 仓库根目录 |
| 核心源码 | `CatTextService.cpp` — 单文件，改造前 1123 行 / 改造后 1808 行 |
| 语言/工具链 | C++（MSVC 2022 BuildTools，`/LD /MT /EHsc /utf-8 /W3`，x64） |
| 输入引擎 | librime（Rime）动态加载，方案 `luna_pinyin` |
| 体系结构 | COM in-proc 文本服务，注册为 `GUID_TFCAT_TIP_KEYBOARD` |
| 界面 | 自绘候选窗（改造前 GDI 实心方块 → 改造后 GDI+ 分层窗口） |
| 特色功能 | "喵化"：在句末把整句改写成喵喵风格（`我`→`本喵`、逐句加`喵`、追加随机颜文字） |
| 宿主环境 | 用户单屏 2560x1440 @ 150% 缩放；主要用于 QQ / 微信聊天 |

**它不是**：AutoHotkey 键盘钩子、安卓侧剪贴板替换、套壳的"假输入法"。
它走的是 TSF 正规路线：`ITfTextInputProcessor` + `ITfKeyEventSink` + `ITfEditSession` + `ITfCompositionSink`，`ITfInsertAtSelection(TF_IAS_QUERYONLY)` 取 range → `StartComposition` → `SetText`。

## 2. 逐项前后对比

### 2.1 触发字符集：逗号为什么"打不出来"

**改造前**

```cpp
static bool IsSentenceEndW(const std::wstring& s)
{
    if (s.empty()) return false;
    wchar_t c = s[s.size() - 1];
    return c == L'。' || c == L'！' || c == L'？' || c == L'!' || c == L'?' || c == L' ';
}
```

**实测结论**：`，` 压根不在这张表里。用真实 `rime.dll` 跑探针，按 `,` 时 Rime 的行为完全正常：

```
ascii=OFF 按 '.' (0x2E) → COMMIT=[。]
ascii=OFF 按 ',' (0x2C) → COMMIT=[，]   ← Rime 侧没问题
```

所以"逗号打不出来"不是引擎问题，是 C++ 侧漏了这个字符。同时 `L' '`（空格）是死条件——空格是 Rime 的选字键，永远不会出现在 commit 末尾。

**改造后**

```cpp
// ── 喵化触发字符集（日常使用）──
// 逗号默认不触发，这是有意的：AddMeowW 内部本来就按「，。！？」分句逐段加「喵」，
// 整句改写一次就能得到「你好喵，今天不错喵 (表情)」。逗号单独触发会让一条消息
// 冒出多个颜文字，而且打字打到一半就眼看着前面的字被改掉。
static bool IsTriggerPunctW(wchar_t c)
{
    return c == L'。' || c == L'！' || c == L'？' || c == L'…' || c == L'；'
        || c == L'!'  || c == L'?'  || c == L';'
        /* || c == L'，' || c == L',' */   // 要开就取消注释
        ;
}

static bool IsSentenceEndW(const std::wstring& s)
{
    if (s.empty()) return false;
    return IsTriggerPunctW(s[s.size() - 1]);
}

// 至少含一个汉字才值得喵化（避免纯标点/纯英文被改写）
static bool HasCJKW(const std::wstring& s)
{
    for (size_t i = 0; i < s.size(); i++)
        if (s[i] >= 0x4E00 && s[i] <= 0x9FFF) return true;
    return false;
}
```

去掉空格（防误触发）、补齐 `；…`、加 `HasCJKW` 守卫。

**为什么逗号不需要触发**——实测输出（从真实源码抽取函数验证，非副本）：

```
原文 [你好，今天天气不错。] → [你好喵，今天天气不错喵。 ˓˓ก(⸍⸌̣ʷ̣̫⸍̣⸌₎ค˒˒]
```

逐句加喵已经由 `AddMeowW` 内部的 `IsSepW` 分句完成了。

### 2.2 Enter 触发（聊天场景的主路径，改造前完全失效）

**改造前**：`ProcessKey` 里 Rime 不处理该键时直接返回，累积的整句被丢弃。

```cpp
if (!g_api->process_key(g_session, keycode, mask))
{
    if (keycode == XK_BackSpace) { if (!m_sessionOriginal.empty()) m_sessionOriginal.pop_back(); }
    else if (visible_ascii)      { m_sessionOriginal += (wchar_t)keycode; }
    else                         { m_sessionOriginal.clear(); }   // ← Enter 走这里
    DbgLog(...);
    return false;                                                 // ← 累积原文到此为止
}
```

Enter 的 `keycode = 0xFF0D ≥ 0xFF00`，落进 `clear()` 分支。**原始日志证据**：

```
[Key]   commit='修' ... session='<已累积的一整句原文>' pending=0
[Key] vk=0x0D keycode=0xFF0D
[Key]   not-handled session=''      ← 整句原文被丢掉，再也不会喵化
```

而聊天就是**打完按 Enter 发送**——主打功能在目标场景里默认不工作。

**改造后**：新增独立的 `EA_TRANSFORM` 编辑动作，在放行 Enter 前先同步改写。

```cpp
enum EditAction { EA_NONE, EA_UPDATE, EA_TRANSFORM };   // 新增 EA_TRANSFORM

bool isEnter = (keycode == XK_Return);
// Shift/Ctrl/Alt+Enter 在聊天里通常是换行而非发送，不该抢先喵化
bool modHeld = ((GetKeyState(VK_SHIFT)   & 0x8000) != 0) ||
               ((GetKeyState(VK_CONTROL) & 0x8000) != 0) ||
               ((GetKeyState(VK_MENU)    & 0x8000) != 0);

if (keycode == XK_BackSpace) { /* 见 2.10 代理对处理 */ }
else if (isEnter) { /* 保留累积原文，不走 clear 分支 */ }
else if (printable) { m_sessionOriginal += (wchar_t)keycode; }
else if (isModifierKey(wParam)) { /* 修饰键不清空 */ }
else { m_sessionOriginal.clear(); }

if (isEnter && !modHeld && HasCJKW(m_sessionOriginal))
{
    m_action = EA_TRANSFORM;
    HRESULT hrInner = S_OK;
    HRESULT hrReq = m_pContext->RequestEditSession(
        m_tfClientId, this, TF_ES_SYNC | TF_ES_READWRITE, &hrInner);
    m_action = EA_NONE;
    if (FAILED(hrReq) || FAILED(hrInner))
        m_sessionOriginal.clear();   // 改写没成功，别留下错位的偏移
}
return false;   // 仍然不吃键，宿主随后发送
```

**关键点**：用 `TF_ES_SYNC` 同步请求编辑会话，改写会在**宿主处理 Enter 之前**落到文档里，所以发出去的已经是喵化后的文本。

**必须用独立的 `EA_TRANSFORM` 而不是复用 `EA_UPDATE`**：`EA_UPDATE` 会拿 `m_commitW` 去写组合，而 Enter 时 `m_commitW` 还是上一次按键的陈旧内容，会重复上屏一个字。

```cpp
STDMETHODIMP DoEditSession(TfEditCookie ec)
{
    if (!m_pContext) return S_OK;
    if (m_action == EA_TRANSFORM) { DoTransform(ec); return S_OK; }   // 只改写，不碰组合
    if (m_action != EA_UPDATE) return S_OK;
    UpdateComposition(ec, m_commitW, m_preeditW);
    if (m_pendingTransform) { DoTransform(ec); m_pendingTransform = false; }
    return S_OK;
}
```

**实测验证**（真实日志，这两条没有句末标点，只可能来自 Enter 路径）：

```
session='早上好'         -> '早上好喵 ฅ(´˚ω˚`)ฅ'
session='很好很有精神'   -> '很好很有精神喵 ฅ(•ω•)ฅ'
```

### 2.3 Shift 抢键 → 感叹号和问号彻底打不出来

**这是最隐蔽的一个。** 表症是"`！` `？` 的触发也没了"，实际是这两个字符**根本产生不出来**。

**改造前**

```cpp
// Shift 切换中英文直输（手动切换 Rime ascii_mode）
if (wParam == VK_SHIFT || wParam == VK_LSHIFT || wParam == VK_RSHIFT)
{
    if (!m_shiftHandled)
    {
        m_shiftHandled = true;
        g_asciiMode = !g_asciiMode;
        g_api->set_option(g_session, "ascii_mode", g_asciiMode ? True : False);
        m_sessionOriginal.clear();       // ← 副作用 2：清空已打好的整句
        m_pendingTransform = false;
    }
    return false;                        // ← 副作用 1：Shift 从不送进 Rime
}
```

**失效链条**（`！` 必须按 `Shift+1`，`？` 必须按 `Shift+/`）：

1. Shift 按下 → 自定义逻辑**抢先把 `ascii_mode` 切成英文**
2. 紧接着的 `1` 在英文模式下被 Rime 直接放行 → **不产生任何 commit**
3. 触发检查写在 `if (!m_commitW.empty())` 里面 → **压根没执行**
4. 同时第 1 步已经把 `m_sessionOriginal` 清空了，整句丢失

**实测证据**：

```
ascii=OFF 按 '!' +ShiftMask          → COMMIT=[！]     ✅ Rime 能出感叹号
ascii=ON  按 '!' +ShiftMask          → handled=0 COMMIT=[-]   ❌ 完全不处理
```

**更关键的发现：Rime 早就把正确的行为配好了**，是这段 C++ 把整条路绕过去了。`rime_data/default.yaml` 里本来就有：

```yaml
ascii_composer:
  good_old_caps_lock: true
  switch_key:
    Shift_L: inline_ascii
    Shift_R: commit_text
    Control_L: noop
    Control_R: noop
    Caps_Lock: clear
    Eisu_toggle: clear
```

**改造方式：删掉自定义逻辑，把 Shift / Caps 原样交还给 Rime。**

```cpp
// VkToRimeKey 里新增映射（原来 Shift/Caps 会掉进 ToUnicodeEx 返回 0）
case VK_SHIFT:
case VK_LSHIFT:
case VK_RSHIFT:
{
    // 左右 Shift 用扫描码区分（左 0x2A / 右 0x36），对应 Rime 的 Shift_L / Shift_R
    UINT scanShift = (UINT)((lParam >> 16) & 0xff);
    keycode = (scanShift == 0x36) ? XK_Shift_R : XK_Shift_L;
    return true;
}
case VK_CAPITAL: keycode = XK_Caps_Lock; return true;
```

```cpp
// 把修饰键的「抬起」转发给 Rime，ascii_composer 靠它实现「单按 Shift 切中英」
void ForwardKeyUp(WPARAM wParam, LPARAM lParam)
{
    if (!g_api || !g_session) return;
    if (wParam != VK_SHIFT && wParam != VK_LSHIFT &&
        wParam != VK_RSHIFT && wParam != VK_CAPITAL) return;
    if (m_lastUpForwarded == wParam) return;          // 去重：转发两次会翻两次，等于没切

    int keycode = 0, mask = 0;
    if (!VkToRimeKey(wParam, lParam, keycode, mask)) return;

    m_lastUpForwarded = wParam;
    g_api->process_key(g_session, keycode, mask | kReleaseMask);   // kReleaseMask 之前定义了但从未使用
    NotifyModeIfChanged();
}
```

**`OnTestKeyUp` 和 `OnKeyUp` 都要转发**（去重保证只翻一次）：按 TSF 惯例，很多宿主只在 `OnTestKeyUp` 返回"已吃掉"时才调 `OnKeyUp`，而本 TIP 永远返回 FALSE——只挂 `OnKeyUp` 的话，Shift 抬起在某些程序里根本收不到。

**实测验证**：

```
Shift_L down              → ascii_mode 不变
Shift_L up(kReleaseMask)  → ascii_mode 0→1     ✅ 单按切中英
Shift_L down #2           → 不变
Shift_L up #2             → ascii_mode 1→0     ✅ 双向

Shift down → 'a' → Shift up  → ascii_mode 保持 0   ✅ 打大写字母不会误切
```

### 2.4 Caps Lock 死锁陷阱：打完英文再也回不到中文

这是"**我打了英文之后后面就不能打中文了**"的真正来源。

`good_old_caps_lock: true` 让"大写锁定开着 = 字母全部直通"，而 `Caps_Lock: clear` 又让它去切 `ascii_mode`。**两个机制叠加后，按一次 Caps 之后无论怎么按都是英文**，而且大写锁定灯亮着用户还看不出来。

**实测（三种配置对比）**

| 配置 | caps#1 后按 `n` | caps#2 后按 `n` | Caps 开着直接按 `n` |
|---|---|---|---|
| `Caps_Lock: clear`（改造前） | `handled=0` 放行（英文） | `handled=0` 放行（英文） | `handled=0` 放行（英文） |
| **`Caps_Lock: noop`（改造后）** | `handled=1 preedit=[n]` ✅ | `handled=1` ✅ | `handled=1 preedit=[ni]` ✅ |

**改法**：`rime_data/default.yaml` 里 `Caps_Lock: clear` → `Caps_Lock: noop`。Caps Lock 还原成普通大写锁定，中英切换交给单按 Shift。

> 注意：改完 `rime_data` 下的配置**必须重建 Rime 部署**，否则运行的是旧编译产物。参数顺序是
> `rime_deployer --build <用户目录> <共享目录>`，**反了会返回 0 但静默什么都不做**。

### 2.5 候选窗每按键闪烁（**改造过程中自己引入的 bug**）

改造 UI 时为了拿到"窗口所在显示器的 DPI"，写了这么一段：

```cpp
// ❌ 错误做法
ShowWindow(g_hCandWnd, SW_HIDE);
SetWindowPos(g_hCandWnd, HWND_TOPMOST, caretRect.left, caretRect.bottom, 8, 8,
             SWP_NOACTIVATE | SWP_NOREDRAW);
```

**每敲一个字：候选框消失 → 缩成一个 8×8 的点 → GDI+ 重画一遍 → 再展开回 550×66 → 重新出现。** 一个 10ms 的窗口状态折腾 × 每秒十几次 = 肉眼可见的一闪一闪。

**改造后**

```cpp
// ✅ 正确做法：layer 窗口的 UpdateLayeredWindow 本身就会原子更新
//    「位置 + 尺寸 + 内容」，不需要先藏再显，更不需要改尺寸。
UpdateLayeredWindow(g_hCandWnd, hdcScreen, &ptDst, &size, hdcMem, &ptSrc, 0, &bf, ULW_ALPHA);
if (!g_candVisible)
{
    // 只在「隐藏 -> 显示」这一刻重新置顶。完全不置顶会被别的置顶窗口压住；
    // 每次按键都置顶则是闪烁的来源。
    SetWindowPos(g_hCandWnd, HWND_TOPMOST, 0, 0, 0, 0,
                 SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_NOREDRAW);
    ShowWindow(g_hCandWnd, SW_SHOWNOACTIVATE);
    g_candVisible = true;
}
```

DPI 改成按插入点查显示器，**完全不碰窗口**：

```cpp
// 动态解析 shcore.dll，Win8.1+ 可用；失败回退 GetDeviceCaps
typedef HRESULT (WINAPI *PFN_GetDpiForMonitor)(HMONITOR, int, UINT*, UINT*);
static int DpiForPoint(POINT pt)
{
    ...
    UINT dx = 0, dy = 0;
    // MDT_EFFECTIVE_DPI = 0
    if (SUCCEEDED(pfn(MonitorFromPoint(pt, MONITOR_DEFAULTTONEAREST), 0, &dx, &dy)) &&
        dx >= 72 && dx <= 960)
        return (int)dx;
    ...
}
```

顺带把每按键的开销也降下来：字体（原来每次新建 6 个 `Gdiplus::Font`）、`StringFormat`、量尺寸用的 DC+位图全部按 DPI 缓存。

### 2.6 候选窗 UI 重做

**改造前**：GDI 实心绘制，白底 + 1px 灰框 + 纯蓝 `RGB(0,120,215)` 实心选中块，固定 `-18px` 微软雅黑，`InvalidateRect` + `WM_PAINT` 重绘。

**改造后**：`WS_EX_LAYERED` + `UpdateLayeredWindow` 的 32bpp per-pixel alpha 分层窗口，GDI+ 绘制。

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 圆角 | 无（直角 + `FrameRect` 1px 灰框） | `GraphicsPath` 抗锯齿真圆角，半径按 DPI 缩放 |
| 阴影 | 无 | 同心圆角矩形叠加的低透明度柔和投影 |
| 选中项 | `RGB(0,120,215)` 纯蓝实心块 + 白字 | `#E8F0FE` 淡蓝圆角药丸 + `#1A56DB` 蓝色序号 + `#102A5E` 深蓝字 |
| 深色主题 | 无 | 读 `AppsUseLightTheme` 自动跟随 |
| DPI | 固定 `-18px`，用 `SM_CXSCREEN` 夹取位置 | 按插入点所在显示器缩放，用显示器**工作区**（`rcWork`）定位 |

| 文字渲染 | `TextOutW` + ClearType | GDI+ `AntiAliasGridFit`（灰阶，因为分层窗口带 alpha，ClearType 的次像素会算错 alpha） |

**配色表**

|---|---|---|
| 卡片底 | `#FDFDFE` | `#2B2D31` |
| 描边 | `#E2E4E9` | `#3C3F44` |
| 候选文字 | `#1C1E22` | `#E7E9EC` |

150% 缩放下 5 个候选的条子为 **439×42 px**（窗口 463×66，含阴影留白）。

### 2.7 改写安全：回读校验

这是全部改动里**唯一涉及数据安全**的一项。

**改造前**：数出累积了多少字，退回去，直接覆盖。从不核对退回去的那一段是不是真的就是累积的原文。

```cpp
// ❌ 盲改
LONG cch = 0;
sel.range->ShiftStart(ec, -(LONG)m_sessionOriginal.length(), &cch, NULL);
sel.range->SetText(ec, 0, transformed.c_str(), (LONG)transformed.length());
```

**风险**：光标位置一旦有偏差（应用自己动过选区、跨字段/段落、只读区、emoji 导致计数漂移），`SetText` 就会**吃掉用户文档里别处的文字**。

**改造后**

```cpp
LONG cch = 0;
sel.range->ShiftStart(ec, -(LONG)original.length(), &cch, NULL);

// —— 回读校验：退够了长度 + 读回来的内容逐字相同，才允许改写 ——
bool ok = (cch == -(LONG)original.length());
if (ok)
{
    wchar_t buf[1024] = { 0 };
    ULONG cchRead = 0;
    if (SUCCEEDED(sel.range->GetText(ec, 0, buf, 1023, &cchRead)) &&
        cchRead == (ULONG)original.length())
    {
        if (original.compare(0, original.length(), buf, cchRead) != 0) ok = false;
    }
    else ok = false;
}
if (!ok)
{
    DbgLog(L"[Xform] 回读校验不通过，放弃改写（宁可不动，也不覆盖别处的文字）");
    sel.range->Release();
    m_sessionOriginal.clear();
    return;
}
```

**设计原则**：宁可这次不喵化，也绝不覆盖用户别处的文字。所有失败路径都会清空 `m_sessionOriginal`，避免留下错位的偏移——这同时保证了 Enter 被调用两次时不会重复改写。

> `ITfRange::GetText` 的签名坑：是 `GetText(ec, dwFlags, pchText, cchMax, pcch)`，
> 参数顺序是 `pchText` 在 `cchMax` **之前**，且后两个是 `ULONG` 不是 `LONG`。
> 见 `msctf.h` 的 `ITfRange_GetText` 宏：`(This, ec, dwFlags, pchText, cchMax, pcch)`。

### 2.9 emoji 退格导致偏移漂移

```cpp
// 改造前
if (keycode == XK_BackSpace)
{
    if (!m_sessionOriginal.empty()) m_sessionOriginal.pop_back();
}
```

退格在应用里删掉的是**一个字符**，而 `std::wstring` 按 UTF-16 code unit 计数：emoji 这类代理对占两个 unit，只 pop 一次会留下半个代理，后面整句的偏移全错。

```cpp
// 改造后
if (keycode == XK_BackSpace)
{
    // 先吃掉低代理，保证 pop 掉的是一个完整字符
    if (m_sessionOriginal.size() >= 2)
    {
        wchar_t last = m_sessionOriginal[m_sessionOriginal.size() - 1];
        if (last >= 0xDC00 && last <= 0xDFFF)
            m_sessionOriginal.pop_back();
    }
    if (!m_sessionOriginal.empty())
        m_sessionOriginal.pop_back();
}
```

### 2.11 构建与部署：改完代码不生效

**改造前**：

- 19 个手工编号的 DLL（`CatTextService2.dll` … `CatTextService18.dll`），**没有版本资源**
- DLL 没有构建脚本，编译命令写在源码注释里，**且注释与实际产物不符**（注释没有 `/MT`，但产物只依赖系统 DLL，是静态 CRT）
- 注册表分裂：`HKLM\...\CLSID\...\InprocServer32` 指向 `CatTextService2.dll`，`HKCU\...` 指向 `CatTextService18.dll`
- `HKLM\SOFTWARE\Classes\WOW6432Node\CLSID\...` **缺失**，但 32 位的 `CTF\TIP` 键存在 → 32 位程序里输入法出现在列表里但选中无反应
- `DllRegisterServer` 所有注册表写入都不检查返回值、永远返回 `S_OK` → 调用方的"注册失败"分支不可达
- 安装器用 `CreateFileW(..., dwShareMode=0, CREATE_ALWAYS)` 释放文件 → DLL 只要被任意进程加载着就 `ERROR_SHARING_VIOLATION`，升级失败

**改造后**：新增 `build.ps1`

```powershell
.\build.ps1                        # 只编译到 _build\CatTextService.dll
.\build.ps1 -Deploy                # 编译 + 部署 + 重新注册（改代码后跑这个）
.\build.ps1 -RebuildRime           # 还改了 rime_data 下配置时加这个
.\build.ps1 -Debug / -NoDebug      # 开关运行时日志
```

关键设计——**换名部署绕过 DLL 占用**：

```powershell
# 正在运行的程序会锁住已加载的 DLL，直接覆盖会 SHARING_VIOLATION。
# 解决办法不是让用户去关程序，而是换个文件名部署、把注册指过去 ——
# 注册表指向哪个文件是我们说了算的。
$target = $deployDll
$n = 0
while ($true) {
    try { Copy-Item $outDll $target -Force -ErrorAction Stop; break }
    catch {
        if ($n -ge 8) { throw "连 $target 都写不进去..." }
        $n++
        $target = Join-Path $root "CatTextService.$n.dll"
    }
}
Set-ItemProperty -Path $hkcuClsid -Name '(default)' -Value $target
```

只改 **HKCU** 的 `InprocServer32`（HKCU 优先级高于 HKLM，不需要管理员），并打印回滚命令。

## 3. 方法论（比结论更重要）

### 3.1 用真实引擎跑行为探针，不要读代码猜

**这一节价值最高。** 上面第 2.1 / 2.3 / 2.4 节的结论，靠读代码全都猜不对——我在第一轮就猜错过一次（把 `，` 的问题归因于触发时机，实际是字符表里根本没这个字）。

做法：直接链接真实的 `rime.dll`，逐个按键喂 `RimeProcessKey`，打印 `handled` / `COMMIT` / `preedit` / 各 option 值。全部探针在 `_probe\` 下（`probe*.cpp`）。

```cpp
static void show(RimeSessionId s, const char* label, int kc, int mask)
{
    Bool h = RimeProcessKey(s, kc, mask);
    printf("  %-30s handled=%d", label, (int)h);
    RIME_STRUCT(RimeCommit, c);
    if (RimeGetCommit(s, &c)) { printf("  COMMIT=[%s]", c.text ? c.text : ""); RimeFreeCommit(&c); }
    RIME_STRUCT(RimeContext, ctx);
    if (RimeGetContext(s, &ctx)) {
        printf("  preedit=[%s] cand=%d", ctx.composition.preedit ? ctx.composition.preedit : "",
               ctx.menu.num_candidates);
        RimeFreeContext(&ctx);
    }
    printf("\n");
}
```

**隔离要点**：用**独立的 `user_data_dir`**（复制一份已编译好的 `build\` 进去避免重新部署）、把 `shared_data_dir` 指向待测配置的副本。**绝不碰线上配置**。

```cpp
traits.shared_data_dir = "<项目根>/rime_data";        // 线上
traits.user_data_dir   = "<项目根>/_probe/user";      // 隔离

// 测配置改动时：复制一份 rime_data 到 _probe/dataX，改它，指向它
traits.shared_data_dir = "<项目根>/_probe/dataX";
traits.user_data_dir   = "<项目根>/_probe/userX";     // 必须新建，否则用旧编译产物
```

编译：

```powershell
cl /nologo /EHsc /utf-8 /I"<项目根>\rime_dl\rime\dist\include" probe.cpp `
   /Fe:probe.exe /link "<项目根>\rime_dl\rime\dist\lib\rime.lib"
# rime.dll 要放在 exe 旁边
```

**踩过的坑**：
- `RimeStartMaintenance(True)` 会全量重建（`stroke.table.bin` 4.5MB，耗时约 30s）；用 `False` 则按时间戳判断
- 测 Caps Lock 要**同时测两种掩码**（带/不带 `kLockMask`），因为 Windows 在 keydown 时锁定状态已经翻转
- 测 Shift 一定要**单独补测"按下→按字母→抬起"**这个序列，只测单按会漏掉"打大写字母误切"这类 bug

### 3.2 离屏渲染验证 UI

看不到屏幕时，把**真实绘制代码**抽出来渲染成 PNG 再核验（`_probe\ui_preview.cpp`）。做法是把 `struct CandTheme` / `MakeTheme` / `AddRoundRect` / `MeasureStr` / `RenderCandWindow` 从源码里**逐行抽取**拼进一个测试程序（不是手抄副本），然后用宏把 `UpdateLayeredWindow` 替换成"存 PNG"：

### 3.4 走过的弯路（别重复）

1. **先猜后验**：第一轮把逗号问题归因于"触发时机"，实际是字符表缺字。**先跑探针再下结论。**
2. **改 UI 时为了量 DPI 去挪窗口** —— 引入了每按键闪烁。**永远不要为了取信息去改窗口状态。**
3. **`edit` 工具会去掉 PowerShell 脚本的 UTF-8 BOM** —— Windows PowerShell 5.1 会把无 BOM 的 UTF-8 当 GBK 读，中文字符串直接语法错误。每次编辑 `.ps1` 后必须补 BOM。
4. **PowerShell 里 `'a'+$x, 'b'+$x` 会因运算符优先级把数组拼成一个字符串** —— 写注册表路径数组时踩过。
5. **`GetDpiForMonitor` 的参数顺序** 和 `rime_deployer --build <用户> <共享>` 的参数顺序都容易写反，后者**反了会静默什么都不做并返回 0**。

## 4. 项目里原本就有、目前仍然存在的问题

这些**没有**修（部分是刻意保留，部分是架构级改动）：

| 问题 | 说明 | 建议 |
|---|---|---|
| `RequestEditSession` 失败时仍然吃键 | `hrReq`/`hr` 只写日志，然后无条件 `return true`。**不能简单改成 `return false`** —— Rime 已经把键吃进 session 了，放行会让宿主再插一个原始字符，变成双输入。实测 `inner` 一直是 0，属理论风险 | 要改得先探测文档可写性 |
| 第一次按键会阻塞 | `EnsureRime()` 在按键回调里跑 `start_maintenance(False)` + `join_maintenance_thread()`，在宿主 UI 线程上做词典部署 | 挪到 `Activate` 异步，或做独立引擎进程 |
| 全局 session + 单一候选窗 | `g_session`/`g_api`/`g_hCandWnd`/`g_candList` 都是文件级全局，而 TSF 会为同一进程的多个文档各建实例 → 同进程两个窗口会串词；候选窗建在第一个 UI 线程上，跨线程操作有挂起风险 | 改成 per-instance |
| in-proc librime | 引擎崩了会带走宿主程序；每个程序一份词典 | 成熟方案是独立服务进程 + IPC（参考小狼毫 Weasel） |
| 32 位宿主不支持 | `WOW6432Node\Classes\CLSID` 缺失但 `WOW6432Node\CTF\TIP` 存在 → 32 位程序里出现在列表但选中无反应 | 补一份 32 位 DLL，或明确不支持 |
| HKLM 有一份指向旧 DLL 的残留注册 | `HKLM\SOFTWARE\Classes\CLSID\{...}\InprocServer32` → `CatTextService2.dll`。HKCU 优先所以日常无感；`DllUnregisterServer` 也不清它 | 管理员 `reg delete` 掉那条 CLSID 键 |
| `我`→`本喵` 是全局替换 | 「我们」→「本喵们」、「自我」→「自本喵」 | 想加例外词表的话在 `TransformText` 里加 |
| 候选框不支持鼠标点选/翻页 | 只有键盘操作 | 需要加命中测试 + 在编辑会话里回写选中项 |

**已修但值得记住的**：`DllMain` 里的 `FreeLibrary(g_hRime)` 已删除——在 DllMain 里释放别的模块要抢加载器锁，是明确的死锁写法；而 `DllCanUnloadNow` 永远返回 `S_FALSE`，本模块只会随进程卸载，系统本来就会收走 rime.dll。

`key_bindings.yaml:37` 有 `{ when: has_menu, accept: period, send: Page_Down }`，而 `default.yaml` 启用了 `paging_with_comma_period`。**后果：候选框开着的时候按 `.` 会被当成"下一页"吃掉，句号打不出来。**

## 6. 如果要继续做

按性价比排序：

1. **按进程名做喵化白名单** —— 只在 QQ/微信里生效，终端、IDE、搜索框保持正常输入。约 20 行（`GetModuleFileNameW` 取宿主进程名 + 一张表）
2. **`RequestEditSession` 失败时的降级策略** —— 先探测文档可写性再决定是否 `process_key`
3. **`start_maintenance` 挪出按键路径** —— 消除首次输入卡顿
4. **把喵化搬进 Rime 的 filter（Lua）** —— 在组合阶段就把文本变成目标文本，彻底不碰宿主文档，安全性最高。代价是要改用小狼毫或给 librime 加 Lua 插件
5. **per-instance 状态** —— 修同进程多文档串词
